# File source background stop (source only)

Added `FileExpertSource::stop_background_after_callers_joined() noexcept` to the shared header/source. Caller must finish and join all foreground reads, dispatch callers, lookahead and mutation/configuration callers and prohibit new calls before invocation. This API proves only the owned background threads were joined; it is not a raw-alias/global producer closure proof.

Terminal seal precedes locks. An allocation-free TLS stack rejects same-owner callback/reentry before touching the nonrecursive close mutex. All worker self IDs are checked before any join. Async prefetches join first while helper IO still exists, then RAM stops/joins, then IO stops/joins. RAM/IO mutexes are released before joins. Concurrent close refuses; join exception is sticky and forbids retry. Repeated successful close succeeds. No thread-vector, job, queue, fd, map, registration or buffer is released by the stop method. Existing running jobs may finish normal updates; queued jobs need not execute after sealing.

Scheduling/start/configuration methods refuse after sealing; queued submissions recheck under their existing worker mutex. This does not support arbitrary racing foreground reads/configuration: caller closure is mandatory. Seal never resets. Default close remains unchanged if explicit terminal close was never used. After explicit terminal close, close requires successful join and enters the existing strict device-drain scope before clearing retained jobs/queues/fds/storage. Unchecked mode requires the caller's GPU drain before destruction. Unknown join is fail-stop in destruction, not silent release.

Source review of DriverWindowRuntime::close_background_after_callers_joined: lookahead -> foresight -> pool -> source -> PLE context close preserves target owners until the following existing GPU drain. Failure short circuits and destructor exits before member destruction. No new ordering defect found under the explicit completed doorbell/dispatch/foreground/controller precondition. Runtime method is not proof those external callers have joined; that orchestration remains the caller's obligation. Successful PLE close does not reset/destroy context guards in this method.
